## 1. Что мы сделали — одно предложение

Мы написали программу, которая каждые 5 секунд читает данные с датчиков и камер дороги, определяет состояние каждого из 86 участков трассы, проверяет безопасность каждого из 72 грузовиков и отдаёт команды — продолжить движение, объехать, встать на стоянку или запросить телеоператора.

## 3. Как работает программа — поток данных

Входной пакет (stdin, NDJSON ~500-600 событий каждые 5 секунд)
   → src/app.py :: main()   [json.loads → state.process_packet]
   → src/core/state.py :: SystemState
       ① update_from_events()
           ├─ SourceHealthTracker  (50 источников)
           ├─ SegmentStateEstimator (86 сегментов)
           ├─ ODDEngine.update()   (погода/RSU)
           └─ HubManager.update()  (хабы)
       ② build_decision_snapshot()
           ├─ ODDEngine.evaluate_all() (72 ВАТС)
           ├─ CorridorRouter.plan_vehicle_actions()
           └─ SafetyGuard.arbitrate_actions()
   → Выходной снимок (stdout, JSON):
       state_estimates [86] | source_assessments [50]
       vehicle_assessments [72] | vehicle_actions [72]

## 4. Модули подробно

### 4.1 src/app.py — точка входа

**Что делает:** читает данные построчно из стандартного ввода (stdin), вызывает обработку каждого пакета, сразу же пишет ответ в stdout.

**Ключевая логика:**
```python
for line in sys.stdin:
    packet = json.loads(line)                        # Прочитать пакет
    decision = state.process_packet(packet)          # Обработать
    sys.stdout.write(json.dumps(decision) + "\n")    # Записать ответ
    sys.stdout.flush()                               # Немедленный сброс (важно!)
```

**Почему это важно:** все диагностические сообщения идут в stderr, а не в stdout.
Это гарантирует, что в выходном потоке будет только чистый JSON.

**Производительность:** среднее время — 11.49 мс при лимите 2000 мс (в 174 раза быстрее).

---

### 4.2 src/sources/health.py — мониторинг источников

**Что делает:** следит за здоровьем 50 источников (детекторы, камеры, метеостанции, RSU, цифровой двойник).

**6 типов сбоев:**

| Тип сбоя     | Когда возникает                | Что делает система        |
|-------------|-------------------------------|--------------------------|
| OUTAGE       | Нет пакетов > 3 тактов        | trust = 0.0, изолирован  |
| PACKET_LOSS  | Потери >= 15%                 | trust снижается          |
| DELAY        | Задержка доставки >= 6 с      | trust = 0.4              |
| TIME_SKEW    | Рассинхрон часов >= 1 с       | Коррекция меток времени  |
| FREEZE       | Значения не меняются > 6 шагов| Данные игнорируются       |
| STALE        | Цифровой двойник устарел >= 25с| Переход на датчики       |

Trust Score — число от 0.0 до 1.0. Источник с trust < 0.3 игнорируется (защита от «ложных» данных).

### 4.3 src/network/estimator.py — оценка состояния дороги

**Что делает:** для каждого из 86 сегментов определяет его состояние.

**Источники данных (в порядке приоритета):**
1. Физические детекторы (ROAD_OBSERVATION) — наивысший приоритет
2. V2X-сообщения от грузовиков (V2X_MESSAGE / ROAD_STATE)
3. Цифровой двойник (DIGITAL_TWIN_SEGMENT) — резервный источник
4. Телеметрия ВАТС (VEHICLE_TELEMETRY) — скорость транспортных средств

**Алгоритм классификации:**
```
Если lanes_open == 0 или детектор сообщил CLOSED:
    → CLOSED  (уверенность 0.99)

Если lanes_open < total_lanes или PARTIAL_BLOCK:
    → PARTIAL_BLOCK  (уверенность 0.98)

Если max_queue >= 25 м И avg_speed <= 65 км/ч:
    → CONGESTED  (уверенность 0.95)

Иначе:
    → OPEN  (уверенность 1.0)
```

**Память между пакетами:** если данных нет — сегмент сохраняет последнее состояние, уверенность постепенно снижается.

### 4.4 src/network/graph.py + router.py — маршрутизация

**graph.py** строит граф дороги. Узлы — сегменты, рёбра — связи между ними.

**router.py** использует алгоритм Дейкстры с учётом:
- Закрытых сегментов (weight = бесконечность)
- Пробок (CONGESTED — вес × 2.2)
- Частичных перекрытий (PARTIAL_BLOCK — вес × 4.0)
- Запрета тоннелей для грузовиков ODD-C профиля

**Action Stability Debounce:** команда меняется только при устойчивом изменении условий. Это предотвращает «дёрганье».

---

### 4.5 src/safety/odd_engine.py — проверка ODD

ODD (Operational Design Domain) — условия, при которых грузовик может ехать автономно.

**4 профиля ВАТС:**

| Профиль | Видимость | Осадки   | V2X       | Ограничения          |
|---------|-----------|----------|-----------|----------------------|
| ODD-A   | >= 100 м  | ур. 0-2  | желателен | нет                  |
| ODD-B   | >= 200 м  | ур. 0-2  | обязателен| только с RSU         |
| ODD-C   | >= 300 м  | ур. 0    | не критичен| запрещены тоннели/мосты |
| ODD-D   | >= 150 м  | ур. 0-1  | обязателен| только открытые сегм.|

**Что проверяется для каждого грузовика:**
видимость, осадки, наличие RSU, качество GNSS, актуальность карты, вес, разрешение проезда через тоннель.

### 4.6 src/safety/guard.py — Safety Gate (финальный фильтр)

Это самый важный модуль. Никакая другая часть системы не может выдать небезопасную команду, если Safety Gate её заблокирует.

**Логика для каждого грузовика:**
```
Грузовик неактивен (на хабе)?
    → NO_ACTION

Хаб назначения перегружен?
    → HOLD

ODD = COMPLIANT?
    → Выполнить команду от роутера (CONTINUE / REROUTE)

ODD = VIOLATED?
    ├── Есть свободный оператор в пуле (всего <= 6)?
    │     → LIMIT_SPEED 40 км/ч + remote_support = true
    └── Пул операторов исчерпан?
          ├── Есть свободная стоянка?
          │     → SAFE_STOP (направить на ближайшую стоянку)
          └── Нет стоянки?
                → HOLD (экстренная остановка на месте)
```

**Критически важно:** CONTINUE никогда не выдаётся при нарушении ODD без оператора. Это обеспечивает **0 критических нарушений**.

### 4.7 src/dispatch/resource_manager.py — диспетчеризация ресурсов

**Пул телеоператоров (<=6 одновременных сессий):**
- Приоритизация: HAZARDOUS > PERISHABLE > HIGH > NORMAL
- Сессия удерживается минимум 3 шага (15 секунд)

**Безопасные стоянки (SS-01..SS-10):**
- Проверка вместимости и грузоподъёмности покрытия
- Избегание стоянок на закрытых сегментах
- Поиск ближайшей доступной через граф

---

### 4.8 src/dispatch/hub_manager.py — управление хабами

4 хаба (HUB-01..HUB-04) — начальные и конечные точки маршрутов.

**Гейтинг выезда (HOLD):**
- Загрузка хаба назначения > 90% → удержать грузовик
- Выезд заблокирован (CLOSED сегмент) → HOLD

## 5. Как считается балл

Скрипт evaluate.py считает **Macro F1** по 4 классам: OPEN, CONGESTED, PARTIAL_BLOCK, CLOSED.

F1 = 2 × Precision × Recall / (Precision + Recall)

**Ключевая особенность:** если система хоть раз ложно определяет CONGESTED
на пустой дороге — F1 для этого класса падает до 0, что снижает итоговый балл на ~25 пунктов.

**Наши результаты:**

|-----------|-------------------------------|---------------|
| TRAIN-001 | Штатный режим                  | 100.00 / 100  |
| TRAIN-002 | Отказы сенсоров, сбои связи    | 92.29 / 100   |

| TRAIN-004 | Масштабное ДТП, дефицит ресурсов| 89.01 / 100  |
| **Средний**|                               | **93.87 / 100** |
