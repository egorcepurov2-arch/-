# ЧАСТЬ 1 — ЗАДАЧА И ОСНОВАНИЯ ДЛЯ АРХИТЕКТУРНЫХ РЕШЕНИЙ

## 1.1 Что требовалось решить

По условиям соревнования нужно было создать **программную систему управления беспилотным грузовым коридором**.

Коридор — это:
- **86 участков дороги** (сегментов) с разной пропускной способностью, типом покрытия и ограничениями по скорости/весу
- **72 автономных грузовика** (ВАТС) с разными профилями допустимых условий работы (ODD)
- **50 источников данных** — физические детекторы, видеокамеры, метеостанции, придорожные RSU-модули, цифровой двойник
- **4 хаба** — начальные и конечные точки маршрутов
- **10 безопасных стоянок** для экстренных остановок
- **6 телеоператоров** — дефицитный ресурс для поддержки грузовиков вне ODD

Формат работы системы — **потоковый Unix-pipeline**: каждые 5 секунд система получает один пакет NDJSON (сотни событий), и должна выдать один JSON-снимок решений за 2 секунды максимум. Никаких БД, никаких облаков, никакого интернета в режиме работы.

## 1.2 Ключевые ограничения, которые определили архитектуру

| Ограничение | Значение | Как повлияло на архитектуру |
|---|---|---|
| Время ответа | <= 2000 мс/пакет | Никакого тяжёлого ML, только алгоритмы |
| Safety Gate | 0 критических нарушений | Отдельный финальный фильтр обязателен |
| Операторов | <= 6 одновременно | Нужен диспетчер с приоритетной очередью |
| Детерминизм | Воспроизводимость | Никаких генераторов случайных чисел |
| Оффлайн | Нет интернета | Все данные грузятся при старте |

## 1.3 На чём строили решение

Мы не использовали ML-модели или нейросети в основной логике. Причина — у них нет формальных гарантий безопасности, и они не объяснимы жюри и регуляторам.

Вместо этого — **детерминированные алгоритмы**:
- Алгоритм Дейкстры для поиска маршрутов
- Взвешенная агрегация данных датчиков с индексом доверия
- Конечный автомат (state machine) для состояний сегментов
- Жёсткие правила для Safety Gate (никаких исключений)

## Модуль 2: `src/app.py` — Точка входа, потоковый цикл

### Что делает
Читает входные пакеты построчно из `sys.stdin`, вызывает `state.process_packet()`, немедленно пишет ответ в `sys.stdout`.

### Ключевые технические решения

**Разделение stdout / stderr:**
```python
# stdout — только чистый JSON для оценщика
sys.stdout.write(json.dumps(decision) + "\n")
sys.stdout.flush()  # Немедленный сброс буфера!

# stderr — диагностика, не попадает в поток решений
print("[INFO] ...", file=sys.stderr)
```
Это критично: оценщик читает stdout, и любой лишний символ вызовет ошибку парсинга JSON.

**Немедленный flush:**
Без `sys.stdout.flush()` Python буферизует вывод. Оценщик ждёт ответа — deadlock. Каждый ответ сбрасывается сразу.

**Обработка ошибок без остановки:**
```python
try:
    decision = state.process_packet(packet)
except Exception:
    decision = state.build_decision_snapshot()  # Всегда выдаём хоть что-то
```
Система никогда не падает без ответа — даже при ошибке выдаёт минимальный корректный снимок.

**Мониторинг производительности:**
```python
if step_duration > 1.5:
    print(f"[WARN] Step {step} took {step_duration:.3f}s (budget: 2.0s)", file=sys.stderr)
```
Предупреждение, если обработка занимает > 75% бюджета.

### Результат производительности
Среднее время обработки: **11.49 мс** при лимите 2000 мс = **запас 174×**.

## Модуль 3: `src/sources/health.py` — Мониторинг источников данных

### Зачем этот модуль
Датчики в реальных системах регулярно выходят из строя, зависают, теряют пакеты или начинают передавать устаревшие данные. Если доверять всем данным без проверки — один сломанный датчик может исказить картину всего коридора.

### Как работает

**Шаг 1 — Сбор телеметрии за шаг**

Для каждого события из пакета:
- Определяется `source_id`
- Рассчитывается задержка доставки: `received_time - event_time`
- Отслеживается смещение часов: `source_clock_offset_ms`
- Для ROAD_OBSERVATION/WEATHER_OBSERVATION собираются последние 8 значений для freeze-теста
- Из INFRASTRUCTURE_HEALTH читается `network_packet_loss_pct` и `last_heartbeat_age_sec`
- Из DIGITAL_TWIN_SEGMENT читается `snapshot_age_sec`

**Шаг 2 — Детекция сбоёв**

Шесть независимых детекторов:

| Детектор | Условие срабатывания | Порог |
|---|---|---|
| **OUTAGE** | NO_HEARTBEAT или heartbeat_age > 60 с | Абсолютный |
| **PACKET_LOSS** | network_packet_loss_pct >= 15% | 15% |
| **DELAY** | avg(последние 5 задержек) >= 6.0 с | 6 секунд |
| **TIME_SKEW** | abs(clock_offset_ms) >= 1000 | 1 секунда |
| **STALE** | только DT-CORE: snapshot_age_sec >= 25 с | 25 секунд |
| **FREEZE** | все 6+ последних значений одинаковы | 6 одинаковых |

**Шаг 3 — Присвоение Trust Score**

```python
if "OUTAGE" in faults:
    status = "FAILED", trust_score = 0.0  # Полное отключение
elif faults:
    status = "DEGRADED", trust_score = 0.4  # Работаем с осторожностью
else:
    status = "OK", trust_score = 1.0  # Полное доверие
```

**Метод get_trust_map()** возвращает словарь `{source_id: trust_score}` который передаётся в estimator.

### Защита от "ложных" данных

Пороги выбраны консервативно. Например:
- DELAY: задержка 6 секунд — это больше одного такта (5 с). Данные из "прошлого" не актуальны.
- FREEZE: 6 одинаковых значений = 30 секунд без изменений. Физически невозможно на работающей дороге.
- PACKET_LOSS 15%: выше этого порога каждый шестой пакет теряется — данным нельзя доверять.

## Модуль 4: `src/network/estimator.py` — Оценка состояния сегментов

### Зачем этот модуль
Это главный аналитический движок. На его выходе — классификация каждого из 86 участков трассы, которая определяет маршруты всех грузовиков и их действия.

### Источники данных и их приоритет

```
Приоритет 1 (высший): ROAD_OBSERVATION
  → Физические детекторы и камеры дороги
  → Дают: speed_kmh, occupancy_pct, queue_estimate_m, lane_count_open_estimate, lane_status

Приоритет 1 (совместно): V2X_MESSAGE типа ROAD_STATE
  → Сообщения от самих грузовиков о состоянии дороги
  → Добавлено в ходе оптимизации (буст +5 баллов)
  → Дают: advisory_speed_kmh, lane_status, queue_estimate_m

Приоритет 2 (резервный): DIGITAL_TWIN_SEGMENT
  → Цифровой двойник, подключается только если нет физических данных
  → Дают: lane_count_open, closure_state, speed_kmh

Приоритет 3 (косвенный): VEHICLE_TELEMETRY
  → Скорость проехавших грузовиков как косвенный индикатор
  → Добавляется к общему пулу скоростей
```

### Алгоритм оценки для одного сегмента

**1. Фильтрация ненадёжных источников:**
```python
trust = source_trust.get(src_id, 1.0)
if trust < 0.3:
    continue  # Источник с трастом < 0.3 игнорируется
```

**2. Сбор физических показателей:**
Из прошедших фильтр событий собираем:
- `speeds` — список скоростей км/ч
- `occupancies` — список занятости полос %
- `queues` — список длин очередей в метрах
- `lanes_open` — минимальное из всех reported значений открытых полос

**3. Fallback на цифровой двойник:**
Если физических детекторов нет или не было сигналов о перекрытии — читаем из DT.

**4. Классификация (в порядке приоритета):**

```python
# Уровень 1: Полное закрытие
if detector_reported_closed or lanes_open == 0:
    return "CLOSED", confidence=0.99

# Уровень 2: Частичное перекрытие
if detector_reported_partial or lanes_open < total_lanes:
    return "PARTIAL_BLOCK", confidence=0.98

# Уровень 3: Пробка (калиброванный порог)
is_congested = (
    (max_queue >= 25.0 and avg_speed > 0 and avg_speed <= 65.0)
    or (avg_occ >= 75.0 and avg_speed > 0 and avg_speed <= 65.0)
)
if is_congested:
    return "CONGESTED", confidence=0.95

# По умолчанию
return "OPEN", confidence=1.0
```

**Почему именно 25м и 65 км/ч:**

Это результат калибровки на TRAIN-003 (туман). В тумане машины замедляются (скорость < 80 км/ч), но очередей нет. До калибровки система ошибочно видела CONGESTED на пустых дорогах в тумане — F1 для класса CONGESTED падал до 0. Порог 65 км/ч отсекает туманное замедление, сохраняя только реальные пробки.

**5. Память между пакетами:**
```python
if not has_fresh_data:
    age_steps = step_index - mem["last_updated_step"]
    if age_steps > 12:  # > 60 секунд без данных
        conf = max(0.5, mem["confidence"] * 0.95)  # Уверенность падает
    # Состояние сохраняется из предыдущего шага
```

Если данных по сегменту нет — последнее известное состояние сохраняется, но уверенность постепенно снижается.

### Ключевое решение по V2X ROAD_STATE

В ходе анализа сценария TRAIN-002 обнаружили, что события `V2X_MESSAGE` с `message_type: ROAD_STATE` содержат ценную информацию о состоянии дороги от грузовиков, которые уже проехали этот участок. Добавили одну строку:

```python
elif ev_type == "V2X_MESSAGE" and ev.get("message_type") == "ROAD_STATE":
    road_obs[sid].append(ev)
```

Это дало +3.5 балла в среднем по TRAIN-002 и TRAIN-004, где физические детекторы частично отказывали.

## Модуль 5: `src/network/graph.py` — Граф дороги и алгоритм Дейкстры

### Структура графа

Граф — **ориентированный** (движение только в одну сторону). Построен как линейный граф на сегментах (line-graph):
- Вершины = сегменты (86 шт.)
- Рёбра = если `сегмент_A.to_node == сегмент_B.from_node` → A ведёт в B

Все рёбра и маппинги вычисляются один раз в `__init__` и хранятся в хэш-таблицах. Это даёт O(1) поиск соседей.

### Алгоритм поиска пути `find_shortest_path()`

Реализован **алгоритм Дейкстры** с использованием `heapq` (бинарная куча).

**Стоимость пути:**
```python
cost = segment.length_m * penalty_multiplier
```

Где `penalty_multiplier`:
- OPEN сегмент: 1.0
- CONGESTED: 2.2 (примерно в 2 раза хуже, чем свободная дорога)
- PARTIAL_BLOCK: 4.0 (лучше объехать)
- CLOSED: ∞ (исключается)

**Ограничения маршрута:**
```python
if vehicle_mass_t > seg.get("weight_limit_t", 44.0):
    continue  # Сегмент не выдержит тоннаж

if seg.get("structure") in forbidden_structures:
    continue  # Запрещённая структура (тоннель для ODD-C)

if not seg.get("av_allowed", True):
    continue  # Сегмент закрыт для беспилотников
```

**Параметр `after_current=True`:**
Поиск начинается со следующих сегментов после текущего положения машины — не нужно учитывать уже пройденный участок.

**Алгоритм поиска ближайшей стоянки `find_nearest_safe_stop()`:**
BFS (поиск в ширину) по смежным сегментам, глубиной до 6 шагов. Проверяет:
- Вместимость стоянки (occupied < capacity)
- Тоннаж машины (vehicle_mass_t <= max_vehicle_mass_t)
- Доступность (сегмент не закрыт)

## Модуль 6: `src/network/router.py` — Маршрутизатор и Action Stability

### Что делает
Планирует конкретные действия для всех 72 ВАТС на основе текущего состояния дорог.

### Алгоритм планирования действий

Для каждого грузовика последовательно:

**Шаг 1 — Неактивная машина:**
```
is_active == False или нет current_segment?
→ NO_ACTION (машина на хабе или ещё не вышла)
```

**Шаг 2 — Машина на закрытом участке:**
```
cur_seg in blocked_segments?
→ Найти ближайшую стоянку через BFS
  Есть стоянка? → SAFE_STOP
  Нет стоянки?  → HOLD + запросить оператора
```

**Шаг 3 — Проверка текущего маршрута:**
```
Есть активный маршрут и он не заблокирован?
→ CONTINUE (не трогаем, машина едет нормально)

Маршрут заблокирован или нет маршрута?
→ Запустить Дейкстру от текущего сегмента
  Найден путь?  → REROUTE (новый маршрут)
  Нет пути?     → искать стоянку
```

### Action Stability Debounce (гистерезис)

Проблема: при кратковременных изменениях трафика маршрут постоянно переключается. Это вызывает "дёрганье" и опасно.

Решение:
```python
DEBOUNCE_STEPS = 6  # 30 секунд гистерезиса

steps_since_reroute = step_index - self.last_reroute_step[vid]
has_congestion = cur_cost > base_len * 1.5  # Путь стал на 50% дороже?

if has_congestion and steps_since_reroute >= DEBOUNCE_STEPS:
    # Ищем альтернативу
    if alt_cost < cur_cost * 0.75:  # Экономия > 25%?
        → REROUTE на новый путь
```

Смена маршрута происходит только если:
1. Прошло минимум 30 секунд с последнего переключения
2. Текущий маршрут стал на 50% дороже базового
3. Альтернатива даёт экономию > 25%

## Модуль 7: `src/safety/odd_engine.py` — Движок ODD

### Зачем нужен

ODD (Operational Design Domain) — это технический стандарт для беспилотных транспортных средств. Каждый грузовик сертифицирован для работы только при определённых условиях. Если условия выходят за рамки — машина не имеет права ехать автономно.

### Предвычисление пространственных маппингов

В `__init__` вычисляются два маппинга, которые остаются неизменными всё время работы:

**1. Сегмент → ближайшая метеостанция** (через Евклидово расстояние):
```python
mid_x = (x1 + x2) / 2.0  # Центр сегмента
mid_y = (y1 + y2) / 2.0
# math.hypot(mid_x - sx, mid_y - sy) → ближайшая станция
```

**2. Сегмент → RSU в зоне покрытия** (через v2x_zone):
```python
zone_to_rsu = {rsu["v2x_zone"]: rsu_id for rsu_id, rsu in self.rsus.items()}
mapping[sid] = zone_to_rsu.get(seg.get("v2x_zone", ""), "RSU-01")
```

### Консервативная оценка погоды

Для каждого грузовика берём **наихудшие** условия по всей группе дорог (`road_group`):
```python
current_vis = min(  # Минимальная видимость в группе
    self.weather_by_station.get(s, {}).get("visibility_m", 1000.0)
    for s in relevant_stations
)
current_rain = max(  # Максимальный уровень осадков в группе
    self.weather_by_station.get(s, {}).get("rain_level", 0)
    for s in relevant_stations
)
```

Если на одной станции MAIN-коридора видимость 60 м — все машины в этой группе дорог считаются в условиях видимости 60 м. Это консервативный подход.

### Проверки ODD для каждой машины (7 проверок)

```python
# 1. Видимость
if current_vis < profile["min_visibility_m"]:
    violations.append("VISIBILITY")

# 2. Уровень осадков
if current_rain > profile["max_rain_level"]:
    violations.append("RAIN")

# 3. Качество GNSS
if gnss_q is not None and gnss_q < profile["min_gnss_quality"]:
    violations.append("GNSS")

# 4. Доступность V2X (только для ODD-B и ODD-D)
if profile["v2x_required"] and not rsu_available[rsu_id]:
    violations.append("V2X")

# 5. Тип структуры (тоннели запрещены для ODD-C)
if seg["structure"] not in profile["allowed_structures"]:
    violations.append("STRUCTURE")

# 6. Ограничение по весу
if vehicle_mass_t > seg["weight_limit_t"]:
    violations.append("WEIGHT_LIMIT")

# 7. Актуальность карты
if map_age is not None and map_age > profile["max_map_age_min"]:
    violations.append("MAP_AGE")
```

| Профиль | Для каких машин | Мин. видимость | Макс. осадки | V2X | Структуры |
|---|---|---|---|---|---|
| ODD-A | Флагман, самые продвинутые | 100 м | уровень 2 | желателен | все |
| ODD-B | V2X-зависимые | 200 м | уровень 2 | обязателен | только с RSU |

```python
# В state.py перед evaluate_all():
```

## Модуль 8: `src/safety/guard.py` — Safety Gate

### Философия модуля

Safety Gate — это **последний и непреодолимый барьер**. Любые предыдущие действия роутера или ошибки в данных не могут обойти его правила. Именно он обеспечивает ноль критических нарушений.

### Алгоритм арбитража для каждой машины

**Сначала — пул операторов:**
```python
# Приоритетный балл = (6 - cargo_priority) * 20 + penalty_per_min
priority_score = (6.0 - cargo_pri) * 20.0 + float(penalty_min)
```
- Груз 1 приоритета (опасный/скоропортящийся): score ≈ 100+
- Груз 5 приоритета (обычный): score ≈ 20+

Кандидаты сортируются по убыванию score, первые 6 получают оператора.

**Затем — решение для каждой машины:**

```
Машина неактивна или нет сегмента?
  → NO_ACTION

Нужен HOLD по хабу?
  → HOLD (хаб перегружен или выезд закрыт)

ODD = COMPLIANT?
  → Выполнить команду от роутера, снять с стоянки если нужно

ODD = VIOLATED + есть оператор в admitted_remote_vids?
  ├── Роутер хотел REROUTE?  → REROUTE + remote_support=true
  └── Иначе?                 → LIMIT_SPEED 40 км/ч + remote_support=true

ODD = VIOLATED + нет оператора?
  ├── Есть стоянка?           → SAFE_STOP на ближайшую стоянку
  └── Нет стоянки?            → HOLD (экстренная остановка на месте)
```

**КРИТИЧЕСКИЙ ИНВАРИАНТ:** Команда `CONTINUE` при нарушении ODD **физически невозможна** в этом коде — она никогда не попадает в ветку `ODD = VIOLATED`.

### Почему приоритизация по (6 - cargo_priority) * 20 + penalty_min

- Коэффициент 20 обеспечивает, что разница в cargo_priority (1–5) перевешивает любые различия в penalty_per_min
- penalty_per_min добавляет тонкую сортировку внутри одного класса приоритета
- Масштаб выбран так, чтобы HAZARDOUS (priority=1) всегда опережал NORMAL (priority=5)

## Модуль 9: `src/dispatch/resource_manager.py` — Диспетчер ресурсов

### RemoteSupportPool — пул телеоператоров

Управляет активными сессиями, строго ограниченными до 6 одновременно.

**Ключевое решение — удержание сессий:**
```python
# Сессии активных кандидатов СОХРАНЯЮТСЯ из предыдущего шага
for vid, sess in self.active_sessions.items():
    if vid in requested_vids:
        retained_sessions[vid] = sess  # Удерживаем!
```

Это важно: если машина получила оператора, она продолжает его иметь пока не нормализуются условия. Без этого каждые 5 секунд происходил бы "перезапуск" арбитража и машины теряли бы операторов посреди манёвра.

**Safety invariant после заполнения:**
```python
if len(self.active_sessions) > self.max_sessions:
    # Принудительно обрезаем по приоритету
    sorted_sessions = sorted(..., key=priority_score, reverse=True)
    self.active_sessions = dict(sorted_sessions[:self.max_sessions])
```

Этот код — последний барьер: даже если где-то выше произошла ошибка и попыталось добавить 7-ю сессию — она будет принудительно вытеснена.

### SafeStopManager — управление стоянками

**Логика назначения:**
1. Если у машины уже есть назначенная стоянка и она всё ещё доступна — оставляем её (стабильность)
2. Иначе ищем через `NetworkGraph.find_nearest_safe_stop()` (BFS)
3. Двойная проверка: сначала граф находит, потом `is_compatible()` подтверждает

**is_compatible() проверяет:**
```python
- stop_id существует в справочнике
- сегмент стоянки не в blocked_segments
- вес машины <= weight_limit сегмента (физика дороги)
- вес машины <= max_vehicle_mass_t стоянки (конструктив)
- текущая занятость < вместимость
```

**sync_occupancies() — синхронизация после каждого шага:**
```python
for vid, stop_id in list(self.vehicle_allocations.items()):
    act = vehicle_actions.get(vid, {})
```

# ЧАСТЬ 4 — ОПТИМИЗАЦИЯ И РАБОТА С МЕТРИКАМИ

## 4.1 Как считается балл

Скрипт `evaluate.py` считает **Macro F1** по четырём классам для оценки состояния сегментов:

```
Классы: OPEN, CONGESTED, PARTIAL_BLOCK, CLOSED

F1(класс) = 2 × Precision × Recall / (Precision + Recall)

Precision = TP / (TP + FP)   — сколько из наших "CONGESTED" реально congested
Recall    = TP / (TP + FN)   — сколько реальных "CONGESTED" мы нашли

Macro F1 = (F1_OPEN + F1_CONGESTED + F1_PARTIAL_BLOCK + F1_CLOSED) / 4
```

**Ловушка Macro F1:** если в ground truth класс `CONGESTED` встречается нечасто, а мы ложно выдаём его на пустых дорогах — Precision для CONGESTED падает к нулю → F1_CONGESTED → 0 → итоговый балл -25 пунктов.

Именно поэтому мы ужесточили порог: **queue >= 25м И speed <= 65 км/ч** одновременно.

## 4.2 Как мы подняли балл с 88.90 до 93.87

**Проблема 1: Ложные CONGESTED в тумане (TRAIN-003)**

В TRAIN-003 — густой туман. Машины едут медленно (50–70 км/ч), но дорога физически свободна. Старый порог: только `avg_speed <= 80 км/ч` — система видела CONGESTED повсюду. F1_CONGESTED ≈ 0.

Решение: ужесточили до `max_queue >= 25м AND avg_speed <= 65 км/ч`. Пробка без очереди — не пробка. +7.53 балла на TRAIN-003.

**Проблема 2: Пропущенные V2X ROAD_STATE (TRAIN-002, TRAIN-004)**

В сценариях с отказами детекторов V2X-сообщения содержали информацию о состоянии дороги, которую система просто игнорировала. Добавили в estimator.py одну строку:

```python
elif ev_type == "V2X_MESSAGE" and ev.get("message_type") == "ROAD_STATE":
    road_obs[sid].append(ev)  # Теперь читаем!
```

+8.53 балла на TRAIN-002, +3.80 на TRAIN-004.
