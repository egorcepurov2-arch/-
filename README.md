## 📌 Регламент и правила работы с Git-репозиторием

Для поддержания стабильности кодовой базы и эффективной командной разработки в проекте принята строгая стратегия ветвления и стандарты работы.

---

### 1. Архитектура веток (Branching Strategy)

* **`master` (или `main`) — Стабильная / Продакшн ветка:**
  * Содержит только готовый, полностью протестированный и рабочий продукт.
  * ⚠️ **Прямой `push` в ветку `master` категорически ЗАПРЕЩЁН!**
  * Изменения в `master` попадают **исключительно** через слияние (Merge / Pull Request) из ветки `dev`.
* **`dev` (develop) — Основная ветка разработки и интеграции:**
  * ⚠️ **Все первоначальные изменения, новый код и фичи ОБЯЗАТЕЛЬНО пушатся в ветку `dev` перед попаданием в `master`.**
  * В этой ветке аккумулируются изменения всей команды и проводятся интеграционные тесты.
* **Тематические ветки (Feature/Fix):**
  * Для каждой отдельной задачи, модуля или исправления создаётся ветка от актуальной `dev`:
    * `feature/<название-задачи>` — разработка нового функционала (например: `feature/auth`, `feature/ui-header`).
    * `bugfix/<название-ошибки>` — исправление багов и дефектов (например: `bugfix/fix-login-error`).
    * `hotfix/<название-исправления>` — срочные исправления критических проблем.

### 2. Рабочий цикл (Workflow)

```mermaid
gitGraph
   commit id: "Initial commit"
   branch dev
   checkout dev
   commit id: "Init dev"
   branch feature/new-logic
   checkout feature/new-logic
   commit id: "feat: add feature logic"
   commit id: "test: verify feature"
   checkout dev
   merge feature/new-logic id: "Merge feature to dev"
   checkout master
   merge dev id: "Release to master"
```

1. **Перед началом работы над задачей:**
   * Переключитесь на ветку `dev` и подтяните последние изменения:
     ```bash
     git checkout dev
     git pull origin dev
     ```
2. **Создайте ветку под задачу:**
   * Ответвитесь от `dev`:
     ```bash
     git checkout -b feature/awesome-feature
     ```
3. **Разработка и фиксация изменений:**
   * Делайте небольшие, логически законченные (атомарные) коммиты.
   * Проверяйте статус и диффы перед фиксацией:
     ```bash
     git status
     git diff
     ```
4. **Интеграция изменений в `dev`:**
   * Перед пушем подтяните актуальный `dev`, чтобы заранее разрешить возможные конфликты локально:
     ```bash
     git fetch origin dev
     git rebase origin/dev  # либо git merge origin/dev
     ```
   * Отправьте ветку на GitHub:
     ```bash
     git push -u origin feature/awesome-feature
     ```
   * Создайте Pull Request в ветку `dev` или произведите слияние в `dev` после проверки.
5. **Релиз в `master`:**
   * Только после того, как функционал в `dev` проверен и полностью работоспособен, создаётся PR/Merge из `dev` в `master`.

### 3. Стандарты сообщений коммитов (Conventional Commits)

Каждое сообщение коммита должно четко объяснять суть изменений. Рекомендуется использовать общепринятые префиксы:

| Префикс | Описание | Пример |
| :--- | :--- | :--- |
| `feat:` | Добавление новой функциональности | `feat: add user registration endpoint` |
| `fix:` | Исправление ошибки | `fix: resolve crash on invalid input` |
| `docs:` | Изменения в документации | `docs: update setup and API guides` |
| `style:` | Форматирование кода (отступы, точки с запятой, без изменения логики) | `style: reformat according to PEP8` |
| `refactor:` | Рефакторинг кода без изменения внешней логики | `refactor: simplify database connection pool` |
| `test:` | Добавление или обновление тестов | `test: add unit tests for auth module` |
| `chore:` | Вспомогательные задачи (обновление зависимостей, сборка, конфиги) | `chore: update docker-compose and .env.example` |

> 💡 **Правило хорошего тона:** пишите сообщение коммита в повелительном наклонении в настоящем времени («add», «fix», «update», а не «added», «fixes»).

### 4. Гигиена репозитория и безопасность

* **Конфиденциальные данные:**
  * Ни в коем случае не коммитить пароли, API-ключи, токены и приватные файлы конфигураций (`.env`).
  * Для демонстрации конфигурации используйте `.env.example`.
* **Файл `.gitignore`:**
  * В репозитории не должно быть скомпилированных файлов, бинарников, системных файлов ОС (`.DS_Store`, `Thumbs.db`), папок IDE (`.vscode/`, `.idea/`), виртуальных окружений (`venv/`, `.venv/`) и кэшей (`__pycache__/`, `node_modules/`).
* **Разрешение конфликтов:**
  * Никогда не решайте конфликты вслепую.
  * Всегда проверяйте работоспособность приложения после слияния веток.

### 5. Шпаргалка по основным командам

```bash
# Проверить текущий статус и ветку
git status

# Переключиться на dev и забрать свежий код
git checkout dev
git pull origin dev

# Создать новую ветку и перейти в неё
git checkout -b feature/my-task

# Зафиксировать изменения
git add .
git commit -m "feat: implement my-task"

# Отправить ветку на GitHub
git push -u origin feature/my-task
```
